THE CHALLENGE

Make tests repeatable—and results understandable.

A request completing successfully is only one piece of evidence. The interface needs to show what ran, what came back, and which conclusions the result can support.

MY CONTRIBUTION

Implementation, integration, and careful validation.

Contributed to a web-based attack simulation interface with Python, FastAPI, HTTP requests, and live event logging. Integrated controlled test execution with response validation and real-time output. Supported generic malicious-request tests and a CVE-2024-4577-style detection check in a controlled environment, applying repeatable testing, troubleshooting, and result documentation.

ENGINEERING DECISIONS

Useful boundaries are part of the design.

The backend uses approved fixed tests, configured target hosts, timeouts, and launch rate limits. The browser cannot supply arbitrary target URLs. Custom Shell runs allowlisted operations rather than OS commands. WebSocket events expose request, response, and completion details. Validation checks status, content type, and expected body text.

EVIDENCE & LIMITS

Execution is only one part of the story.

A separate read-only Threat Intelligence application consumes genuine honeypot records through JSONL or an internal HTTP adapter; a configured event source is required. It does not treat panel output as detection evidence. A successful response check does not prove exploitation, sensor action, or Elasticsearch ingestion. The separate public simulation produces no genuine traffic or detections.

TRY THE PROJECT

The public repository includes backend and frontend setup commands, target configuration, and verification guidance. A configured lab backend is required. This portfolio does not run attacks.
